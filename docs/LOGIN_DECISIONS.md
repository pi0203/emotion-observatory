## 4-2. 중단 기록과 삭제: 열린 질문 (2026-10-10)

- **서버에서도 지워져야 한다.** 중단 화면의 "이 기록을 지우기"는 지금 이 기기에서 그 기록을 지운다(2026-10-10 수정, PRODUCT_SPEC §16).
  중단 기록을 서버에 올린다면, 이 버튼은 서버의 같은 기록도 지워야 한다. 서버 삭제가 실패하거나 늦을 때 화면에 어떻게 알릴지, 7번의 비동기 위험(삭제 전에 새로고침)과 함께 정해야 한다.
- **사용자가 알고 선택해야 하는가.** 중단은 사용자가 스스로 멈춘 기록이다. 멈춘 기록이 서버로 간다는 것을
  - 로그인 때 한 번 알리면 충분한가,
  - 중단 화면에서 다시 알려야 하는가,
  - 중단 기록만 따로 올리지 않을 선택을 주어야 하는가.
- 입구에서 바로 멈춘 기록(`stopReason: "entry"`)은 내용이 거의 없다. 이것도 올릴지 따로 볼 수 있다.

## 5. 보관 기간과 삭제

| 질문 | 확인할 점 |
|---|---|

| 개별 기록 삭제 | 서버에서 실제로 지워지는가, 얼마나 걸리는가. 백업에 남는 기간(서비스별로 확인 필요) |
| 전체 삭제, 계정 삭제 | PRODUCT_SPEC §16의 "export / delete all"을 계정에서도 제공한다. 삭제 후 되돌릴 수 없음을 고지해야 한다 |
| 오래 쓰지 않은 계정 | 자동 삭제할지, 한다면 얼마 뒤에 어떻게 미리 알릴지 |

| 삭제 요청 대응 | 이메일 주소를 잃은 사용자가 삭제를 요청하면 어떻게 본인 확인을 할지 |

## 6. 동의 문구

문구 초안을 확정하려면 아래를 먼저 정해야 한다. 이 문서는 문구를 쓰지 않는다.

- 게스트 상태에서는 아무 경고도 보이지 않는다(스펙 원칙). 로그인을 누른 사람에게만 설명한다.
- 반드시 알릴 것: 무엇이 서버로 가는지, 어디에 저장되는지, 얼마나 보관되는지, 어떻게 지우는지, 이메일 주소를 어떻게 쓰는지.
- 동의를 한 번에 받을지, 로그인 때와 가져오기 때를 나눌지.
- 개인정보 처리방침 문서가 필요한지, 누가 검토하는지(법률 검토 필요 여부는 확인 필요).
- 만 14세 미만 등 연령 관련 안내가 필요한지(확인 필요). (2026-10-19) 앱의 나이 입장은 [PRODUCT_SPEC §2 「나이」](../PRODUCT_SPEC.md)에 적었다. 로그인을 붙이기 전에 만 14세 미만 처리 방식(개인정보 보호법 제22조의2, 법정대리인 동의)을 먼저 정한다.
- 제품 톤: 안심시키는 표현이나 효과 약속을 하지 않는다. "안전합니다" 같은 단정 표현은 근거 없이 쓰지 않는다.

## 7. 동기와 비동기 (Phase 2 전에 정할 기술 결정)

Phase 0은 동기 `StorageAdapter`로 만들었다. 서버 저장은 비동기라서 Phase 2에서 아래 중 하나를 고른다.

| 선택지 | 내용 | 위험 |
|---|---|---|
| A. 로컬은 동기, 계정 저장은 별도 비동기 계층 | 게스트 경로는 그대로 두고, 로그인 상태에서만 비동기 계층을 추가 | 화면 코드가 두 경로를 구분해야 한다 |
| B. 인터페이스 전체를 비동기로 | 호출 지점을 `await`로 바꾼다 | 아래 위험을 모두 받는다 |

B의 위험(코드를 읽고 확인한 것):
- reducer는 순수 함수이고 저장은 `useEffect`에서 하므로 reducer 자체는 바뀌지 않는다. 바뀌는 곳은 `app/page.tsx`의 호출 지점이다.
  `showRecords`, `saveFollowUp`, 첫 로드의 `loadDraft`, 그리고 `persistSession` effect.
- `persistSession` effect가 연속으로 실행되면 비동기 저장이 서로 앞지를 수 있다. 직렬화(대기열)가 필요하다.
- 중단 화면의 `이 기록을 지우기`는 `removeDraft(); dropCompleted(id); window.location.reload();`를 곧바로 실행한다.
  비동기가 되면 삭제가 끝나기 전에 새로고침되어 기록이 남을 수 있다. 2026-10-10에 고친 버그(PRODUCT_SPEC §16)와 같은 종류가 다시 생길 수 있다.
- `lib/migrations.ts`와 기존 테스트 대부분이 동기 호출을 쓴다. 기존 테스트를 수정 없이 통과시키려면 동기 래퍼를 유지해야 한다.
- 실패 처리(네트워크 오류, 저장 실패)를 화면에 어떻게 보일지가 새로 필요하다. 지금은 실패 상태가 없다.

## 8. SAFETY.md 갱신

현재 SAFETY.md는 "localStorage는 보호 수단이 아니다"까지만 말한다. 서버 저장 전에 갱신해야 한다.

- 서버에 저장되는 기록이 위기 관련 표현을 포함할 수 있는 점과, 그에 대한 책임 범위(앱은 위기 대응 도구가 아니라는 현재 입장을 유지하는가).
- 서버 보관 데이터를 누가 볼 수 있는지(운영자 접근 정책).
- 유출 사고가 났을 때의 대응 절차와 사용자 고지 방법.
- 개인정보 영향평가 또는 법률 자문이 필요한지(확인 필요).
- 일반 감정 관찰 데이터와 safety 관련 입력의 분리 원칙(SAFETY.md에 이미 "향후 설계"로 있는 항목)을 서버 저장에도 적용할지.
- 공유 기능(읽기 전용 링크)을 만들 때 링크 유효 기간, 취소 방법.

  - 초안 4-C는 "직접 입력한 어휘(`personalMeaning`) 빈도"를 수집한다고 적는다. 결정 기록은 `personalMeaning`을 서버에 올리지 않기로 했다. 내용이 아닌 **횟수**만이라면 괜찮은지 정해야 한다.
  - 초안 4-C는 "로컬 익명화 추출"을, 결정 기록은 서버 저장을 말한다. 연구 자료를 서버 기록에서 가져올지, 기기에서 따로 내보낼지 정해야 한다.
  - 초안 6번은 위험 신호가 있을 때 안전 리소스 화면을 띄운다고 적는다. [SAFETY.md](../SAFETY.md)는 위험도를 자동으로 판별하지 않는다고 적는다. 연구에서 이 둘을 어떻게 맞출지 임상가 검토가 필요한지(확인 필요).

## 11. 수업 채널(A) 설계 초안 (2026-10-10)

**결정이 아니라 초안이다.** 서비스(인증, DB, 이메일)는 고르지 않았다. "확인 필요"는 교수님이나 학교에 아직 확인하지 않았다는 뜻이고, 법률이나 윤리 판단은 하지 않는다.

### 11-1. 수집 허용 목록

목록에 있는 것만 보낸다. 목록에 없는 것은 보내지 않는다.

| 항목 | 형태 | 메모 |
|---|---|---|
| 참여자 식별 | 이메일 또는 이름 | 어느 쪽으로 할지 **확인 필요**. 로그인 방식(이메일 코드)을 쓰면 이메일은 이미 갖게 된다 |
| 이용 날짜 | 날짜만 (예: 2026-10-10) | 시각은 보내지 않는다. 앱의 기록에는 시각(`createdAt` 등)이 있으므로, 보낼 때 날짜로 잘라야 한다 |
| 도달한 단계 | 거칠게 묶은 이름 | 아래 후보 중에서 정한다. 정하지 않았다 |

**도달한 단계를 묶는 후보.** 코드의 실제 단계 이름(`lib/session-types.ts`의 `Stage`)은 18개다:
`landing`, `quick-affect`, `quick-candidates`, `quick-summary`, `coach-appraisal`, `coach-words`, `coach-note`,
`entry`, `entry-mini`, `body`, `affect`, `context`, `meaning`, `emotion`, `outcome`, `summary`, `support`, `stopped`.

| 묶음 후보 | 들어가는 단계 |
|---|---|
| 빠른 확인 | `quick-affect`, `quick-candidates`, `quick-summary` |
| 표현 사이의 차이 (Coach) | `coach-appraisal`, `coach-words`, `coach-note` |
| 깊은 성찰 (Deep Reflection) | `entry`, `entry-mini`, `body`, `affect`, `context`, `meaning`, `emotion`, `outcome`, `summary` |
| 필요한 것 살펴보기 | `support` |
| 보내지 않음 | `landing`(아직 시작하지 않음), `stopped`(중단했다는 사실은 모으지 않는다) |

정할 때 볼 점:
- **기록의 `stage` 값을 그대로 보내면 안 된다.** 마지막 `stage`가 `stopped`이면 중단했다는 사실이 드러난다.
  대신 기록에 어떤 부분이 있는지(`quickCheck`, `coach`, `deepReflection`, `support`)로 "어디까지 써 봤는지"를 만들 수 있다.
  지금 코드에도 비슷한 계산(`sessionDepth`: 빠른 확인 / 빠른 확인 + 자세히 / 자세히)이 있다.
- 깊은 성찰 입구(`entry`)에서 "지금은 그만 생각하고 싶어요"를 고르면 `deepReflection` 없이 끝난다. 이 경우를 "깊은 성찰에 도달"로 셀지 정해야 한다. 세면 중단 사실이 간접적으로 드러날 수 있다.
- 묶음을 더 거칠게(예: "빠른 확인만 / 더 써 봄") 하면 드러나는 것이 줄어든다.

### 11-2. 수집하지 않는 것

감정 단어(제시된 것과 직접 적은 것 모두), 몸 감각, 맥락(상황 글과 그 종류), 자유서술 전부, `personalMeaning`,
중단했다는 사실과 그 이유, 시각 정밀도(날짜보다 자세한 시간), 기기 정보(기종, 브라우저, IP 등).
Affect Pad 위치, 요약 평가, 고른 필요와 대응, Coach의 선택도 감정 내용에 가까우므로 모으지 않는다.

### 11-3. 보이는 범위

- 이용 정보(날짜, 도달한 단계)는 **본인과 수업 운영자**만 본다.
- 운영자가 누구인지(교수님, 본인, 또는 둘 다)는 **확인 필요**.
- 운영자가 동료일 때의 문제: 본인이 수업을 함께 듣는 동료이면서 운영자라면, 동료들은 서로의 이용 정보를 같은 학생이 본다는 것을 알게 된다. 써 보지 않은 사실이 동료에게 드러나 부담이 될 수 있다. 운영자 접근을 날짜와 단계로만 제한하는지, 이름 대신 가명으로 보는지 정해야 한다.

### 11-4. 동료에게 보일 것: 항목별 선택 (후보)

- 의견, 자기소개, 써 봤다는 사실을 동료에게 보일지는 **항목마다 본인이 고르는** 구조를 후보로 둔다.
- 기본값은 **운영자만**. 동료에게 보이는 것은 본인이 켤 때만이다.
- 고른 것을 나중에 끌 수 있어야 한다. 끄면 동료 화면에서 사라진다.

### 11-5. 감정 기록 자체의 공유 (나중 단계)

본인이 공유하고 싶다고 한 것에 들어 있지만, A의 첫 단계에는 넣지 않고 별도의 나중 단계로 둔다. 그때의 조건:
- 기록마다 본인이 **명시적으로** 공유한다. 자동으로 공유되지 않는다.
- 공유하는 순간에만, 본인이 고른 필드의 **복사본**을 올린다. 원본 기록은 계속 기기에만 있다.
- 읽기 전용이다.
- 자유서술, `personalMeaning`, 관계 관련 내용은 기본 제외한다(PROJECT_CONTEXT §11의 공유 원칙). 관계 관련 내용의 정의는 4-1의 열린 질문과 같다.
- 공유를 철회하면 서버의 복사본을 지운다.
- **열린 질문:** 동료에게 어디까지 보이는가(운영자만 / 고른 동료 / 수업 전체).

### 11-6. 게스트 경로는 변하지 않는다

- 로그인하지 않으면 네트워크 전송이 없다. 지금처럼 기록은 기기에만 남는다.
- 로그인한 뒤에만, 내용 없는 이용 기록(11-1)만 보낸다.
- 본인이 자기 이용 기록을 보고 지울 수 있어야 한다.

### 11-7. 로그인할 때 보여줄 안내에 들어갈 것

- 무엇이 전송되는지: 식별 정보, 이용 날짜, 도달한 단계. 감정 내용은 전송되지 않는다는 것.
- 누가 보는지: 본인과 수업 운영자(누구인지 이름으로). 동료에게는 본인이 고른 것만.
- 언제 지워지는지: 학기 종료 후 처리(11-8)와 본인이 직접 지우는 방법.
- 로그인하지 않아도 앱을 똑같이 쓸 수 있다는 것.

### 11-8. 학기 종료 후 처리와 삭제 요청

- 학기가 끝나면 이용 기록과 공유한 의견, 소개를 지울지, 얼마 뒤에 지울지 정한다.
- 본인이 삭제를 요청하면 이용 기록, 공유한 것, 계정을 지운다. 운영자가 내려받아 둔 사본이 있다면 그것도 지우는지 정한다.

### 11-9. 교수님께 확인할 점 (확인 필요)

- 수업에서 참여자 정보(이름 또는 이메일, 이용 날짜, 도달한 단계)를 모아도 되는 범위. **확인 필요**
- 운영자 역할을 누가 맡는지, 학생이 운영자여도 되는지. **확인 필요**
- 동의를 어떻게 받는지, 참여하지 않아도 불이익이 없다는 것을 어떻게 알리는지. **확인 필요**
- 수업 활동에서 외부 서비스에 학생 정보를 두는 것에 대한 학교 정책. **확인 필요**

### 11-10. PRODUCT_SPEC §16 문구와의 관계

지금 §16은 MVP 기본값으로 "no account required"와 "no analytics containing free-text emotion content"를 적고 있다.
A는 계정을 요구하지 않고(게스트 유지), 감정 내용이 담긴 분석도 하지 않으므로 지금 문구와 어긋나지 않는다.
다만 로그인한 참여자의 이용 기록이 생기므로, A를 만들게 되면 아래처럼 덧붙이는 것을 제안한다. **지금은 §16을 바꾸지 않는다.**

> 제안 문구: "no account required. 로그인한 참여자에게만, 감정 내용이 없는 이용 기록(이용 날짜와 도달한 단계)을 남긴다."

### 11-11. 로그인 없는 간단한 대안 (먼저 준비)

공유 시트나 설문으로 같은 목적의 일부를 먼저 할 수 있다. **앱 밖에서** 하고, 앱에는 분석을 넣지 않는다.

| 열 | 내용 |
|---|---|
| 이름 또는 별명 | 본인이 적는다 |
| 써 본 날짜 | 날짜만 |
| 어디까지 써 봤는지 | 빠른 확인 / 표현 사이의 차이 / 깊은 성찰 / 필요한 것 살펴보기 중 고르기 (11-1의 묶음 후보와 맞춘다) |
| 의견 | 앱에 대한 의견 |
| 자기소개 (선택) | 적지 않아도 된다 |

감정 기록 내용을 적는 열은 두지 않는다. 시트를 동료끼리 함께 볼지, 운영자만 볼지는 11-3, 11-4와 같은 질문이다.

### 11-12. 점검 질문: 식별과 편집 권한 (2026-10-26)

2026-10-26 본인 결정으로 더했다. 다른 앱 점검에서 「이름 + 휴대폰 끝 4자리」로 들어가는 방식과, 사이트 편집 권한이 있는 사람이 참가자 기록에 닿는 문제가 보였다([CROSS_PROJECT_2026_10_26.md](CROSS_PROJECT_2026_10_26.md) b). 답은 정하지 않았다. A를 만들기 전에 답한다.

- **같은 수업의 동료가 맞힐 수 있는 정보를 식별에 쓰는가?** 이름처럼 서로 아는 정보나 휴대폰 끝 4자리처럼 경우의 수가 적은 정보를 「비밀」로 쓰면, 동료가 다른 사람으로 들어갈 수 있다. 11-1의 「이메일 또는 이름」을 정할 때 함께 본다.
- **사이트 편집 권한이 있는 사람이 참여자 기록을 볼 수 있는가?** 코드·배포·DB 설정을 바꿀 수 있는 사람(저장소 관리자, Vercel·DB 계정 소유자)은 접근 규칙과 상관없이 기록에 닿을 수 있다. 볼 수 있다면 그 사람을 11-3의 「보이는 범위」와 11-7의 「누가 보는지」에 적는가?
