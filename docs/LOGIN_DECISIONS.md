# 로그인 방향 A: Phase 1 전에 정해야 할 것

작성일: 2026-10-10. 이 문서는 선택지와 확인할 점만 적는다. 서비스를 고르거나 가입하지 않았고,
조사하지 않은 서비스의 기능, 가격, 정책은 단정하지 않는다. "확인 필요"는 아직 확인하지 않았다는 뜻이다.

기준: [PROJECT_CONTEXT.md §11](../PROJECT_CONTEXT.md), [PRODUCT_SPEC.md §16](../PRODUCT_SPEC.md), [SAFETY.md](../SAFETY.md).
이미 정해진 것(게스트 유지, 이메일 6자리 코드부터, 가져오기는 반드시 묻기, 공유는 개별 읽기 전용부터)은 다시 묻지 않는다.

## 0. 먼저 알아둘 것

- [AUTH_SPEC_PHASE0_1.md](AUTH_SPEC_PHASE0_1.md)는 특정 인증/DB 서비스를 "권장"으로 적고 있다. 이것은 다른 세션이 쓴 제안이고,
  본인이 선택한 것이 아니다. 아래 1, 2번에서 다시 고른다.
- 그 문서의 스키마 초안은 `status`를 `draft`/`completed` 둘로 제한한다. 지금 코드에는 `stopped`(중단 기록)도 있고,
  [tests/storage.test.ts](../tests/storage.test.ts)가 그 저장을 확인한다. 초안 스키마를 쓰려면 `stopped`를 어떻게 다룰지 정해야 한다.
- 그 문서의 인터페이스는 비동기다. Phase 0에서는 동기 인터페이스로 만들었다. 이유와 선택지는 7번.
- 지금 앱은 초안을 한 자리(`emotion-lab:draft:v4`)에만 둔다. 서버에도 "초안 한 개"만 둘지, 여러 개를 허용할지 정해야 한다.

## 1. 인증 방식

이미 정해진 것: 이메일 6자리 코드. 남은 질문:

| 질문 | 선택지 | 확인할 점 |
|---|---|---|
| 직접 만들 것인가, 외부 서비스를 쓸 것인가 | 직접 구현 / 관리형 인증 서비스 | 직접 구현하면 코드 만료, 시도 횟수 제한, 재전송 제한, 세션 쿠키 보안을 모두 맡는다. 서비스별 기능과 한도는 확인 필요 |
| 코드 유효 시간과 시도 횟수 | 예: 몇 분, 몇 번 | 너무 짧으면 메일 지연 때 실패하고, 너무 길면 위험하다. 값은 정해지지 않았다 |
| 세션 유지 기간 | 짧게 / 길게 / 선택 | 공용 기기에서 기록이 보이는 위험과 재로그인 번거로움의 균형 |
| 로그아웃 시 이 기기의 로컬 기록 | 그대로 / 계정 기록 캐시만 지우기 | 계정 기록을 이 기기에 캐시한다면 로그아웃 때 지워야 한다. 캐시 여부 자체를 정해야 한다 |
| 이메일 주소를 바꾸거나 잃어버렸을 때 | 지원하지 않음 / 복구 절차 | 복구를 지원하면 본인 확인 방법이 또 필요하다 |

## 2. DB와 접근 규칙

| 질문 | 선택지 | 확인할 점 |
|---|---|---|
| 어디에 저장하는가 | 관리형 DB / 직접 운영 DB | 서비스별 지역(리전), 백업 방식, 직원 접근 가능 여부는 확인 필요 |
| 데이터 위치 | 국내 / 해외 | 한국 개인정보 관련 법령상 국외 이전 고지가 필요한지 확인 필요(법률 검토 대상) |
| 본인 것만 보이게 하는 규칙 | DB 수준 행 단위 규칙 / 서버 코드에서만 검사 | PROJECT_CONTEXT §11: 표를 만들 때 함께 건다. 나중으로 미루지 않는다 |
| 저장 형식 | 기록 전체를 JSON 한 덩어리로 / 필드별 컬럼 | JSON이면 v4 형식 보존이 쉽다. 컬럼이면 조회가 쉽지만 마이그레이션(v5 이후)이 어려워진다 |
| 민감 필드 암호화 | 전송, 저장 시 기본 암호화만 / 앱 수준 추가 암호화 | PRODUCT_SPEC §16은 "encryption"을 요구한다. 어디까지를 뜻하는지 정해야 한다. 앱 수준 암호화는 키를 누가 갖는지(복구 불가 가능성)도 정해야 한다 |
| 운영 로그 | 기록 내용을 로그에 남기지 않음 | PRODUCT_SPEC §16: 자유 서술을 제3자 로그에 남기지 않는다. 쓰려는 서비스의 요청/에러 로그에 본문이 섞이지 않는지 확인 필요 |

## 3. 이메일 발송

| 질문 | 확인할 점 |
|---|---|
| 발송을 누가 하는가 | 인증 서비스 내장 발송 / 별도 발송 서비스. 각각의 일일 한도, 신뢰도(스팸함으로 가는지)는 확인 필요 |
| 발신 도메인 | 직접 소유한 도메인이 있는가. 없다면 발신 주소를 어떻게 할지. SPF/DKIM 등 설정이 필요한지는 확인 필요 |
| 메일 본문 | 6자리 코드와 최소 안내만 담는다. 기록 내용이나 감정 관련 문구를 메일에 넣지 않는다 |
| 메일 주소의 성격 | 이메일 주소도 개인정보다. 수집 목적, 보관, 삭제를 동의 문구에 넣어야 한다 |
| 남용 방지 | 같은 주소/IP로 반복 요청하는 경우의 제한을 정해야 한다 |
| 한국어 안내 | 메일 제목과 본문 문구 확정 (제품 톤: 판정하지 않고 권하지 않는다) |

## 4. 서버 저장 범위

가장 중요한 결정이다. 서버에 저장하는 순간 기록은 지켜야 할 민감 정보가 된다.

| 질문 | 선택지 | 확인할 점 |
|---|---|---|
| 무엇을 올리는가 | 완료 기록만 / 완료 + 중단 기록 / 초안까지 | 초안은 작성 도중의 생각까지 서버로 간다. 중단 기록(`stopped`)은 사용자가 멈춘 기록이라 올릴지 따로 정해야 한다 |
| 자유 서술과 `personalMeaning`, 관계 관련 내용 | 그대로 / 서버에서 제외하고 기기에만 / 필드별 선택 | 공유에서는 기본 제외로 정했다. 저장에서도 같은 원칙을 쓸지 정해야 한다 |
| 동기화 방식 | 서버가 기준 / 기기가 기준 / 마지막 수정 우선 | 두 기기에서 같은 `id`를 고치면 충돌한다. 지금 `saveCompleted`는 id 기준 덮어쓰기다 |
| 오프라인 | 로그인 상태에서 오프라인이면 로컬에 먼저 저장하고 나중에 올림 / 막음 | 나중에 올리는 방식이면 중복과 순서 문제가 생긴다 |
| 가져오기(Phase 3) | 전부 / 선택 / 중복 처리 | 같은 `id`가 이미 서버에 있을 때 어느 쪽을 남길지. 가져오기 후 이 기기 기록을 지울지는 사용자가 정한다(자동 삭제 금지) |
| 분석, 통계 | 하지 않음 / 개인정보를 뺀 집계만 | PRODUCT_SPEC §16: 자유 서술을 포함한 분석 없음. 효과 검증(PROJECT_CONTEXT §12)에 쓸 계획이 있으면 별도 동의가 필요하다 |

## 5. 보관 기간과 삭제

| 질문 | 확인할 점 |
|---|---|
| 기록 보관 기간 | 무기한 / 기한 설정. 기한이 있다면 사용자에게 어떻게 알리는가 |
| 개별 기록 삭제 | 서버에서 실제로 지워지는가, 얼마나 걸리는가. 백업에 남는 기간(서비스별로 확인 필요) |
| 전체 삭제, 계정 삭제 | PRODUCT_SPEC §16의 "export / delete all"을 계정에서도 제공한다. 삭제 후 되돌릴 수 없음을 고지해야 한다 |
| 오래 쓰지 않은 계정 | 자동 삭제할지, 한다면 얼마 뒤에 어떻게 미리 알릴지 |
| 내보내기 | 서버 기록을 내려받는 형식과 방법 |
| 삭제 요청 대응 | 이메일 주소를 잃은 사용자가 삭제를 요청하면 어떻게 본인 확인을 할지 |

## 6. 동의 문구

문구 초안을 확정하려면 아래를 먼저 정해야 한다. 이 문서는 문구를 쓰지 않는다.

- 게스트 상태에서는 아무 경고도 보이지 않는다(스펙 원칙). 로그인을 누른 사람에게만 설명한다.
- 반드시 알릴 것: 무엇이 서버로 가는지, 어디에 저장되는지, 얼마나 보관되는지, 어떻게 지우는지, 이메일 주소를 어떻게 쓰는지.
- 동의를 한 번에 받을지, 로그인 때와 가져오기 때를 나눌지.
- 개인정보 처리방침 문서가 필요한지, 누가 검토하는지(법률 검토 필요 여부는 확인 필요).
- 만 14세 미만 등 연령 관련 안내가 필요한지(확인 필요).
- 제품 톤: 안심시키는 표현이나 효과 약속을 하지 않는다. "안전합니다" 같은 단정 표현은 근거 없이 쓰지 않는다.

## 7. 동기와 비동기 (Phase 2 전에 정할 기술 결정)

Phase 0은 동기 `StorageAdapter`로 만들었다. 서버 저장은 비동기라서 Phase 2에서 아래 중 하나를 고른다.

| 선택지 | 내용 | 위험 |
|---|---|---|
| A. 로컬은 동기, 계정 저장은 별도 비동기 계층 | 게스트 경로는 그대로 두고, 로그인 상태에서만 비동기 계층을 추가 | 화면 코드가 두 경로를 구분해야 한다 |
| B. 인터페이스 전체를 비동기로 | 호출 지점을 `await`로 바꾼다 | 아래 위험을 모두 받는다 |

B의 위험(코드를 읽고 확인한 것):
- reducer는 순수 함수이고 저장은 `useEffect`에서 하므로 reducer 자체는 바뀌지 않는다. 바뀌는 곳은 `app/page.tsx`의 호출 지점이다.
  `showRecords`, `saveFollowUp`, 첫 로드의 `loadDraft`, 그리고 `persistSession` effect.
- `persistSession` effect가 연속으로 실행되면 비동기 저장이 서로 앞지를 수 있다. 직렬화(대기열)가 필요하다.
- 중단 화면의 `이 기록을 지우기`는 `removeDraft(); dropCompleted(id); window.location.reload();`를 곧바로 실행한다.
  비동기가 되면 삭제가 끝나기 전에 새로고침되어 기록이 남을 수 있다. 2026-10-10에 고친 버그(PRODUCT_SPEC §16)와 같은 종류가 다시 생길 수 있다.
- `lib/migrations.ts`와 기존 테스트 대부분이 동기 호출을 쓴다. 기존 테스트를 수정 없이 통과시키려면 동기 래퍼를 유지해야 한다.
- 실패 처리(네트워크 오류, 저장 실패)를 화면에 어떻게 보일지가 새로 필요하다. 지금은 실패 상태가 없다.

## 8. SAFETY.md 갱신

현재 SAFETY.md는 "localStorage는 보호 수단이 아니다"까지만 말한다. 서버 저장 전에 갱신해야 한다.

- 서버에 저장되는 기록이 위기 관련 표현을 포함할 수 있는 점과, 그에 대한 책임 범위(앱은 위기 대응 도구가 아니라는 현재 입장을 유지하는가).
- 서버 보관 데이터를 누가 볼 수 있는지(운영자 접근 정책).
- 유출 사고가 났을 때의 대응 절차와 사용자 고지 방법.
- 개인정보 영향평가 또는 법률 자문이 필요한지(확인 필요).
- 일반 감정 관찰 데이터와 safety 관련 입력의 분리 원칙(SAFETY.md에 이미 "향후 설계"로 있는 항목)을 서버 저장에도 적용할지.
- 공유 기능(읽기 전용 링크)을 만들 때 링크 유효 기간, 취소 방법.

## 9. 결정 순서 제안

1. 4번(서버 저장 범위)과 5번(보관, 삭제)을 먼저. 나머지 선택이 여기에 달려 있다.
2. 1, 2, 3번(인증, DB, 이메일)에서 서비스 후보를 좁히고, 후보마다 확인 필요 항목을 실제로 조사한다.
3. 7번(동기/비동기)은 서비스를 정한 뒤에.
4. 6, 8번(동의 문구, SAFETY.md)은 Phase 1 배포 전에 끝낸다.
