# 디자인 정렬: 감정 관찰실을 홈페이지와 같은 사이트로 느껴지게

작성일: 2026-10-11. 브랜치 `claude/design-alignment`. **이 문서는 감사와 설계만 담는다. 앱 코드(app/, lib/, tests/, CSS)는 바꾸지 않았다.**
모든 제안은 본인 결정 전의 후보다. 말투 후보(6절)는 본인과 교수님 검토가 필요하다.

## 0. 목적과 제약

- 목적: 홈페이지(eunchanjoe.vercel.app)와 같은 사이트로 느껴지게 한다. 지금 이질감의 큰 원인은 색(거의 흰 바탕 #FCFDFB와 형광 연두 #B4FF00), 글꼴(Georgia와 시스템 기본), 틀(메뉴와 꼬리말 없음), 말투다.
- 제약: 감정이 올라온 순간에 쓰는 화면이다. 홈페이지의 장식과 시각적 소음은 가져오지 않는다(9절). [PRODUCT_SPEC §19](../PRODUCT_SPEC.md)의 대비 기준(본문 4.5:1, 큰 글자 3:1, 조작 요소 경계와 초점 표시 3:1)과 「색만으로 상태를 알리지 않는다」는 그대로 지킨다.
- 홈페이지 값의 출처: 별도 표시가 없으면 본인이 운영 사이트의 실제 스타일에서 읽어 준 값이다(소스 코드 기준 아님). 글꼴 전송량과 머리말 높이는 2026-10-11에 운영 사이트를 직접 열어 쟀다.

## 2. 값 대응표와 대비

### 2-1. 제안

토큰 **이름은 그대로 두고 값만 바꾼다.** 화면 코드와 시험이 토큰 이름을 쓰기 때문이다. 밝게는 홈페이지의 sage를 기본으로, 어둡게는 홈페이지의 어두운 값을 쓴다. 홈페이지에 그 역할을 하는 값이 없거나 홈페이지 값이 대비 기준에 못 미치는 곳은 **새 값(★)** 으로 표시했다. 새 값은 홈페이지 값을 조금 진하게 하거나 밝게 해서 만든 것이고, 본인 결정이 필요하다.

- 지금의 sage 위에서 기존 조작 요소 경계 #7E9487은 2.6:1이다. 그래서 ★ #66795f로 진하게 한다.
- 어둡게에서 주 단추를 #8c3b22로 채우면 단추 가장자리가 바탕과 2.30:1이라 잘 안 보인다. 그래서 어둡게에서는 밝은 채움(#d0764b)에 어두운 글자로 뒤집는다. 밝게에서는 홈페이지처럼 어두운 채움에 밝은 글자다.
- 직접 쓴 색 16곳도 토큰으로 옮긴다: `white` 5곳은 `--card`, 좌표판 그러데이션과 테두리는 `--card`, `--paper`, `--line-strong`, 축선과 그림자의 연두 rgba는 `--line`, 임시 단어 안내 글자 #5C5F4E는 `--muted`, 확인 창 막과 그림자는 지금처럼 어두운 rgba(바탕색과 무관하게 같은 뜻)로 두되 어둡게에서 막을 조금 더 진하게.
- 형광 연두 #B4FF00은 앱 어디에도 남기지 않는다.

## 3. 유지할 구분 점검

새 색에서 각 구분이 **색 말고 무엇으로** 유지되는지 보았다.

| 구분 | 색 말고 유지되는 근거 | 새 색에서의 판정 |
|---|---|---|
| Coach 「예시 / 내 선택 / 참고 설명」 | 실제 글자 라벨(「예시 상황」, 「예시 연습 결과」, 「내 선택」), 경계 모양(예시: 얇은 선과 3px 모서리, 내 선택: 진한 조작 경계와 12px 모서리, 참고: 왼쪽 세로선만) | 유지됨. 단 색으로 생기던 차이는 줄어든다(아래 위험 1) |
| 선택됨과 선택 안 됨 (선택지, Coach 칩) | 테두리 색 + 안쪽 1px 테두리(두께 2px로 보임) + Coach에서는 ✓ 글자 + `aria-pressed` | 유지됨 |
| 선택됨과 선택 안 됨 (가능한 표현 칩, 몸 칩, 상황 종류, 도움 여부) | 테두리 색 + 안쪽 1px 테두리. **✓ 글자 없음** | 약해짐(위험 2) |
| 감정 좌표판의 영역 | 가운데 가로세로 축선 + 네 방향 글자 라벨(에너지가 올라온 느낌, 가라앉은 느낌, 불쾌함, 유쾌함). 영역마다 색을 칠하지 않는다 | 유지됨. 지금 연두 그러데이션이 사라져도 뜻은 잃지 않는다 |
| 좌표 점 | 크기(20px), 굵은 테두리, 바탕색 고리 | 유지됨 |
| 진행 | 「1 / 6」 글자 + 막대 | 유지됨 |
| 단계 안내(`step-note`), 원칙 문단(`why-principle`) | 왼쪽 3px 세로선 + 바탕 | 세로선이 지금 형광 연두(`--accent`)다. 새 강조색으로 바꾸면 유지됨 |
| 예시 안내(`example-notice`) | 굵은 첫 문장 + 왼쪽 세로선 | 유지됨 |
| 기록 깊이 배지 | 글자(빠른 확인, 자세히) | 유지됨. 어둡게에서는 본문색 글자로(2-2) |
| 오류와 알림(기록 옮기기) | 글자 문장 + `role="alert"`/`status` | 유지됨 |

**흐려질 위험이 있는 곳**

1. **예시 영역과 카드와 선택됨 바탕이 거의 같은 밝기다.** 밝게에서 예시 영역(warm)과 카드 사이 1.14:1, 선택됨과 카드 사이 1.01:1, 선택됨과 예시 영역 사이 1.12:1이다. 어둡게에서는 1.04, 1.14, 1.10이다. 지금도 바탕만으로는 차이가 작지만, 새 값에서는 **바탕색으로 생기는 구분이 사실상 없다.** 라벨과 경계가 일을 다 해야 한다.
2. **✓ 없는 칩의 선택 상태.** 가능한 표현, 몸 감각, 상황 종류, 도움 여부, 맞는 정도 선택지는 선택될 때 테두리 색과 두께만 바뀐다. 바탕 차이가 1.01:1로 줄면, 색을 잘 구별하지 못하는 사람에게는 두께 1px 차이만 남는다. 제안: 1단계에서 Coach처럼 ✓ 글자를 모든 선택 칩과 선택지에 붙인다(화면 글자가 늘어나므로 본인 확인 필요).
3. **예시 영역(blush)과 선택됨(blush 표면)이 같은 계열의 분홍이다.** Coach에서 예시 영역 바로 아래에 선택된 칩이 오면, 「예시 쪽」과 「내가 고른 것」이 같은 색 계열로 보일 수 있다. 라벨과 경계로 구분은 남지만, 색의 연상은 섞인다. 대안: 선택됨 바탕을 sage 표면보다 한 단계 밝은 값으로 두고 강조 테두리만 쓰기(새 값이 하나 더 필요).
4. **좌표판의 경계.** 지금은 연두 그러데이션과 #7F9A44 테두리로 판이 또렷하다. 바탕(sage)과 판(sage 표면)의 차이는 1.09:1이라, 판의 윤곽은 조작 경계색(3.77:1) 테두리에 기대게 된다. 테두리 굵기를 1px에서 줄이지 않는다.
5. **어둡게의 강조 글자 여유.** 예시 영역 위 강조 글자가 4.56:1로 기준에 겨우 걸친다. 예시 영역 안에는 강조 글자를 쓰지 않는 규칙(지금 보조 글자에 쓰는 규칙과 같은 방식)을 둔다.
6. **눈썹 글자(eyebrow)와 펼침 제목(why summary)이 강조색 글자다.** 지금은 짙은 녹색, 제안은 적갈색이라 모든 화면 머리에 적갈색이 흩어진다. 홈페이지는 강조색을 아껴 쓰므로, 눈썹 글자를 보조색으로 바꾸는 것도 검토할 만하다(결정 필요).
7. **시험 하나가 옛 색의 사실을 확인한다.** `tests/coach-zones.test.tsx`의 「keeps --muted off --warm」는 「`--muted`가 `--warm` 위에서 4.5:1에 못 미친다」를 기대한다. 새 값에서는 6.43:1이 되어 이 기대가 틀려진다. 규칙(예시 영역에 보조색을 쓰지 않는다)은 그대로 둘 수 있지만, 그 이유를 말하는 기대값은 바꿔야 한다(8절, 열린 질문).

## 4. 글꼴 정렬

### 4-1. 지금 글꼴이 운영체제마다 어떻게 보이나

- 본문 `Georgia, "Times New Roman", serif`: Georgia는 영어 글자만 갖고 있다. **한국어 글자는 각 기기의 기본 한글 글꼴로 대신 그려진다.** macOS와 iOS에서는 보통 Apple SD Gothic Neo(고딕) 계열, Windows에서는 맑은 고딕, Android에서는 Noto Sans CJK나 제조사 글꼴이다. 그래서 영어 숫자와 문장부호는 세리프(Georgia)인데 한국어는 고딕인, 섞인 모양이 된다. 기기마다 다르게 보이는 것이 정상인 상태다.
- 단추, 라벨, 작은 글자 `system-ui, sans-serif`: 기기의 시스템 글꼴(macOS는 SF와 Apple SD Gothic Neo, Windows는 Segoe UI와 맑은 고딕, Android는 Roboto와 Noto Sans CJK).
- 이 앱은 지금 **글꼴 파일을 하나도 받지 않는다**(아래 실측 0KB).

### 4-2. 홈페이지 글꼴 (2026-10-11 운영 사이트 실측)

운영 홈페이지 첫 화면과 「나」 화면을 열어 브라우저가 실제로 불러온 글꼴을 확인했다.

| 화면 | 불러온 글꼴 | 글꼴 파일 수 | 글꼴 전송량 | 전체 전송량 |
|---|---|---|---|---|
| 홈페이지 첫 화면 `/` | Noto Sans KR 400, 500 / Noto Serif KR 400 / Instrument Serif 400 / songMyung 400 | 32 | 597KB | 1,145KB |
| 홈페이지 「나」 `/me/` | Noto Sans KR 400, 500, 700 / Noto Serif KR 400 / Instrument Serif 400 | 43 | 842KB | 1,417KB |
| 감정 관찰실 첫 화면 | 없음 (Georgia, system-ui) | 0 | 0KB | 174KB |

- 홈페이지는 한국어 글꼴을 글자 범위(unicode-range) 조각으로 나눠 싣는다. 그래서 화면에 나온 글자가 많을수록 받는 조각이 늘어난다(첫 화면 32조각, 「나」 43조각).
- 본인이 관찰한 값에는 「영어 글은 Newsreader」가 있는데, 이번에 연 두 화면에서는 Newsreader가 불려 오지 않았고 Instrument Serif가 쓰였다. 영어 글 화면에만 있는 것인지 확인이 필요하다(열린 질문).

### 4-3. 제안

- 홈페이지가 이미 싣는 글꼴과 굵기만 쓴다: 제목 Noto Serif KR 400, 본문과 단추 Noto Sans KR 400과 500. 지금 600, 700으로 쓰는 굵은 글자(14곳)는 500으로 맞춘다. 700은 새 굵기를 늘리는 것이라 쓰지 않는다.
- 싣는 방법: `next/font/google`로 `Noto_Sans_KR({ weight: ["400", "500"] })`, `Noto_Serif_KR({ weight: "400" })`를 루트 레이아웃(`app/(ko)/layout.tsx`, 한국어 문서 틀 `app/korean-document.tsx`)에서 불러 CSS 변수로 넘긴다. next/font는 글꼴 파일을 이 앱의 주소에서 내보내므로(외부 글꼴 서버로 요청하지 않음) 「외부로 요청하지 않는다」는 원칙과 맞는다. 이 부분은 착수 전에 `node_modules/next/dist/docs`의 글꼴 문서로 다시 확인한다.
- 영어 화면은 Noto Sans KR의 라틴 글자를 그대로 쓰거나, 홈페이지 영어 글과 같은 글꼴을 쓸지 정해야 한다(열린 질문).
- **예상 전송량(추정):** 첫 화면에서 글꼴만 대략 **0.3~0.6MB 늘 것으로 추정한다.** 근거는 홈페이지 첫 화면이 비슷한 양의 한국어 글자로 597KB(글꼴 넷)를 받는다는 점이고, 이 앱은 그중 둘(Sans 400과 500, Serif 400)만 쓰므로 그보다 적을 것이다. 지금 전체 전송량이 174KB이므로 첫 화면 전송량이 2~4배가 될 수 있다. **이것은 추정이다. 실제로는 개발 도구의 네트워크 탭(또는 이번 감사에서 쓴 측정 스크립트)으로 운영 미리보기에서 재야 한다.** 늘어난 양이 크면 제목에만 Serif를 쓰고 본문은 시스템 글꼴로 두는 절충도 비교한다.
- 첫 글자가 늦게 뜨는 문제를 피하려고 `display: "swap"`과 대체 글꼴 크기 맞춤(next/font 기본)을 쓴다.

**결정과 실측 (2026-10-12, 본인 결정):** 대안 3을 골랐다. Noto Sans KR 400과 Noto Serif KR 400만 싣는다(굵기 500은 싣지 않는다).
처음 여는 새 브라우저에서 첫 화면 글꼴 215KB, 풀이 39단계 전체 422KB(문서안 Sans 400·500 + Serif 400은 317KB와 605KB로 기준 600KB를 넘었다).
글자 크기는 이 절의 네 단계(aside, body, lead, scene)에 **small(.875rem)을 더한 다섯 단계**로 했다. 문서와 다른 점이다. 이유: 지금 14~15px인 안내와 메모 글자를 body(16px)로 올리면 화면이 길어지고, aside(12px)로 내리면 읽기 어려워진다.
굵은 얼굴이 없으므로 `<strong>`(문구 사전의 `<b>`)는 브라우저가 만드는 굵게(합성)로 보인다. 대안(강조색, 밑줄, CSS만 변경)은 본인 결정 대기.

## 5. 틀 (머리말, 메뉴, 꼬리말)

### 5-1. 규칙 제안

| 화면 | 보일 것 |
|---|---|
| 첫 화면, 지난 기록, 기록 상세 | 홈페이지와 같은 로고, 메뉴, 꼬리말 |
| 풀이 중(빠른 확인부터 요약, 지금 필요한 것, Coach, 그만하기 확인까지) | 지금처럼 최소한만: 앱 이름과 「한 단계 뒤로」, 「그만하기」, 진행 막대 |
| 그만했을 때 | 최소 틀(자리를 떠나는 화면이라 메뉴로 다른 곳을 권하지 않는다) |

- 첫 화면과 지난 기록은 「여기가 어디인지」를 알리는 자리라 홈페이지 틀이 도움이 된다. 풀이 화면은 한 화면 한 과제(PRODUCT_SPEC §19)라 틀이 과제를 밀어내면 안 된다.
- 메뉴 이름과 순서는 홈페이지와 같게 하고, 감정 관찰실이 메뉴의 한 칸으로 들어갈지는 홈페이지 쪽 결정이다.

**구현 (2026-10-12, 브랜치 `claude/design-font-shell`):** 첫 화면, 지난 기록, 기록 상세에 홈페이지 머리말(로고 「Eunchan Joe」, 메뉴 Me, Reading, Threads, Map, 홈페이지로 같은 탭에서 이동)과 작은 꼬리말(앱 이름, 「조은찬」, 홈페이지 링크)을 붙였다. 꼬리말에 메일 주소와 라이선스 문구는 넣지 않는다. 풀이 중 화면, Coach, 중단 화면은 지금의 최소 틀 그대로다. 로고는 새 글꼴을 싣지 않고 앱의 제목용 명조(Noto Serif KR 400)로 쓴다(홈페이지 로고는 Instrument Serif).
- **위기 상담 안내의 자리: 결정 대기.** 이 틀(꼬리말)에는 넣지 않는다. 화면 안내 문구는 별도 브랜치 `claude/safety-note`에서 첫 화면, 중단 화면, 「더 불편해짐」 화면에 넣는 안이 검토 중이며, 이 브랜치와 합칠 때 자리를 다시 맞춘다.

### 5-2. 근거: 메뉴가 풀이를 밀어낸다 (캡처 측정)

운영 사이트에서 빠른 확인 첫 화면을 열고, 브라우저 안에서만 홈페이지 머리말 높이만큼의 빈 칸을 위에 끼워 넣어 위치를 쟀다(코드는 바꾸지 않았다). 홈페이지 머리말 높이는 운영 홈페이지 「나」 화면에서 직접 잰 값이다(375폭 144px, 1280폭 154px).

| 화면 크기 | 머리말 | 감정 좌표판 위치(위~아래) | 첫 화면에 보이는 판 높이 | 「다음」 단추 아래 끝 |
|---|---|---|---|---|
| 375 x 667 | 없음(지금) | 383~675 | 284px / 292px | 809 (스크롤 필요) |
| 375 x 667 | 있음(144px) | 527~819 | 140px / 292px | 953 (스크롤 필요) |
| 1280 x 800 | 없음(지금) | 462~817 | 338px / 355px | 951 (스크롤 필요) |
| 1280 x 800 | 있음(154px) | 616~971 | 184px / 355px | 1105 (스크롤 필요) |

- 휴대폰 크기(375 x 667)에서 머리말을 얹으면, 첫 화면에 보이는 좌표판이 284px에서 140px로 **절반 아래로** 줄어든다. 판을 누르려면 먼저 스크롤해야 한다.
